# Round 18 — SIM Blockball: Differential Isolation (modem-ver-18)

## The decisive experiment
**Stock modem restored on the SAME phone, RIL, and card:**
- `gsm.sim.state = READY`
- IMSI = 432110906760882 (43211 = MTN Irancell)
- Full SMS/broadcast flow active
=> The AP side (kernel CCCI, gsm0710muxd, mtkrild, framework) is 100% capable.
**Our V24 r12c-prod is the sole cause of the SIM stall.**

## What OUR modem does achieve (all verified live)
- Card detect: PRESENT (EINT/driver OK)
- USIM app: listed, type USIM — but `APPSTATE_DETECTED, PINSTATE_UNKNOWN`
- APDU passthrough: EF_ECC reads succeed through our modem; framework read
  **ICCID 89981109000067608823** and parsed ECC records
- Stall point: modem's own USIM app init between DETECTED → PIN-known;
  never reads EF_IMSI, never sends SIM-ready (+EIND 128-class) URC
- Every APDU returns sw=0x91 0x34 (proactive pending) — modem never FETCHes

## Ruled out this round
- UIM NVRAM LID skew: ULM* = UL1 MIPI TPC RF records (not SIM); MT0X=band info
- MT80/MT81 SBP (SIM personalization) records: deleted → regenerated → same
- SAT presence: RSAT compiled in; sim_task/usim driver present both sides
- eSIM/eUICC feature skew: no euicc symbols in either image
- String-level parity: EIND/EUSIM/ESIMS/HOT_PLUG/EINT refs all present

## Remaining suspects (ranked)
1. **CCCI RPC version skew**: our tree is MOLY W1423 (2014-06); stock is
   2508-era (2015-08). The V24 SIM init may wait on a modem↔AP RPC the
   2015 HTC kernel answers differently (SIM hot-plug RPC: ccci_rpc_it.c
   references MD1_SIM1_HOT_PLUG_EINT). Need modem-side trace to confirm.
2. USIM app-activation sequence difference (terminal-profile/FETCH policy)
   vs the card's expectation (0x91 0x34 = 52-byte proactive pending).
