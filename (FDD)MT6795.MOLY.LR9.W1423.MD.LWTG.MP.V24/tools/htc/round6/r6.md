# Round 6 — Event-Table Investigation (2026-09-19 late, modem-ver-11 cont.)

## Question
Does the RFD_MIPIevent.c:134 @FMC DSP assert clear once HTC's MIPI
EVENT tables are also ported (data tables were done in R5)?

## What was tried
1. **Structural event transplant (binary)**: located our LTE/UMTS event
   tables authoritatively (ELF symbols; img = va - 0xf276d000 + 0x833870
   verified on multiple anchors). Stock side via per-band va-delta from
   data anchors: only 6/26 sites were event-shaped (HTC link layout
   differs) — UMTS RX events (4x288B) + 2 TPC events landed; LTE events
   didn't map.
2. **Direct stock event discovery**: found stock's true HTC event tables
   by shape-scan (12B events: elm,st,sp,type + u16 timing; e.g. B5 TX
   events @stock 0x8ab930: 6 events incl PA+ASM+TFC combinations ours
   never had). KEY FINDING: stock event tables are LONGER (6+ events vs
   our 4-event/48B and 3-event/36B slots) — binary grafting cannot carry
   HTC's full sequences into fixed-size V24 slots.
3. **NVRAM-regen combination test**: diag-all-mipi (HTC data + partial
   events) + cleared 12 stale MIPI NVRAM files (force regen from new
   defaults): boot was clean ~5 min, then assert returned after NVRAM
   regeneration cycle. Eliminates "stale NVRAM masks transplant" theory.

## Conclusion (evidence-backed)
The DSP assert validates EVENT tables; HTC's event sequences do not fit
our V24 fixed-size table slots. **The remaining path to SIM READY is a
source-level port**: rewrite lte_custom_mipi.c / ul1d_custom_mipi.c /
l1d_custom_mipi.c event arrays with HTC's decoded values (now extracted:
stock event blobs + their layouts), rebuild MOLY on the
exp/htc-rf-transplant branch (patched libephy.a already committed there),
repackage with the no-asserts patch set, retest.
