# Round 21 — UDF Probe Bisection: Park Point Found (modem-ver-21)

## Method: UDF crash-probes on the prod base
Patch 2 bytes (`UDF #0xEE`) at a function entry in r12c-prod; boot; read
dmesg. Crash with `fatal error code 2` = address inside that function →
it EXECUTED. Clean boot → it NEVER RAN. Asserts stay silenced; the UDF
still traps (exception type 1, offender SIM). Verified method on
terminal_profile first.

## Probe results (exact execution map of our modem's SIM init)

| Step | Function | Result |

## THE PARK POINT
Our USIM init executes: card detect → terminal profile → proactive
FETCH machinery → STATUS → **PIN verify** → … then never issues the
first EF SELECT. Everything before works; everything after is dead.

Interpretation: after verify_chv the SIM entity should transition to
"session ready" and start reading EFs (IMSI etc). Instead it parks.
Candidates for the missing transition:
1. verify_chv response never arrives/decodes (sw != expected) — e.g.
   the card answers 0x91xx "proactive pending" to the VERIFY and our
   old lib treats it as failure/ignores instead of FETCH-then-retry
2. The "app ready" message to itself (queue) is lost (stock's [SIM Q]
   instrumentation exists precisely around this)
3. A USIM-specific post-PIN state (e.g. reading EF_DIR/ADF select via
   select_id) gated by a condition that's false in our build.

## Corrections to earlier rounds
- R18/R19 "never FETCHes" was WRONG: the 0x91 0x34 sw belongs to the
  RIL-proxy APDU channel, not the modem's own session. FETCH runs.
- R20 "older lib missing recovery" is secondary: recovery exists in
  our libsim.a (sim_start_recovery_timer etc. found in sim_handler.obj
  strings); the [SIM Q]/HTCDBG strings are HTC trace-level additions.
