**Q: Does CCCI answer all requests correctly and read modem status
successfully — or is a READY answer being silenced/corrupted/interrupted?**

**A: CCCI is fully healthy. No READY is being produced, let alone lost.**

### Transport-layer health checks (all clean)
- CCCI channel counters (ch12/14/15, AT/FS/message): flowing, no stalls
- ccci_fsd (file service): 541 unique op patterns, zero errors, active
  read/write cycles — FS channel NOT hung (my earlier freeze read was a
  log-window artifact, corrected)
- Zero exceptions/asserts in dmesg; no CCCI error lines
- AT command path: requests reach RIL proxies (verified via ATCI proxy
  wake + muxd LackofAtciChannel trace)
- RPC channels: traffic counters active

### The verdict on "silenced/interrupted/corrupted"
The modem's status answer is **truthfully NOT_READY**:
- It enumerates the card (num_apps=1, type USIM) → SIM task ran
- It passes APDUs with genuine card data → transport + card both fine
- It reports APPSTATE_DETECTED / PINSTATE_UNKNOWN → its own USIM app
  state machine is parked between "app detected" and "PIN known"
- No SIM-ready URC is generated because the state never changes —
  nothing to deliver. No URC is queued and dropped (verified: UNSOL
  channels idle, not erroring)

**The stall is INSIDE the modem's USIM init sequence, not the transport.**

## Residual technical observations
- Every APDU returns sw=0x91 0x34 ("proactive command pending, 52B") —
  the modem never FETCHes the pending proactive command. A card waiting
  for its proactive session can stall app init exactly here. SAT is
  compiled in (RSAT=MODEM_WITH_RSAT) but the FETCH policy may differ.
- SIM_OPEN_CHANNEL (AID-based) answered NO_SUCH_ELEMENT — secondary clue
  of app-session handling differences.
