# Round 10 — NVRAM Keystone + My-Own-Bug-Fix (modem-ver-15)

## What was identified as "still left" (and why)
The modem's runtime RF tables = compiled defaults OVERLAID by phone NVRAM.
Phone NVRAM had stock-W15.06 records: EL1A (EL1_CTRL_REG_RW - the LTE RF
custom-override mask) + EL4N-Q + MT3K-Q. V24 misreads them -> ephy:171.
ALSO: EL1A regenerates as 0xFF garbage by default (NVRAM_EF_FF_DEFAULT).

## What was done
1. Identified EL1A = EL1_CTRL_REG_RW via nvram_data_items.c block scan.
2. Source fix: EL1A default FF->ZERO (no overrides; runtime = pure
   compiled HTC-ported defaults). Commit on exp/htc-rf-transplant.
3. Rebuilt (r10), re-applied GGE/UMTS transplants + no-asserts set.
4. Cleared the 13 RF NVRAM files; r10 boot CRASHED type(2) swi.
5. ROOT-CAUSED THE SWI: fatal error code 2 = 0x3fb5ac = inside my nopped
   kal_assert_fail veneers. THOSE VENEERS ARE ARM-MODE; my Thumb 'bx lr'
   (70 47) = undefined instruction in ARM -> swi trap. (R3-C's luck: no
   assert ever reached them. With NVRAM cleared, a different assert did.)
6. r10b: proper ARM 'bx lr' (1e ff 2f e1) at the 3 ARM veneers.
7. Verified simultaneously: fresh EL1A on phone = ZEROS; built B5 TX row0
   = stock HTC values byte-exact (source port IS live in the build).

## Result of r10b (on phone now)
- ZERO exceptions, stable, baseband reports MOLY V24.
- RF/MIPI/NVRAM chain: FULLY CONSISTENT for the first time.
- SIM: still NOT_READY. Registration state = searching (voice reg 2).
- The stall is now UIM-level (past RF): SIM app detected (USIM) but PIN
  state unknown / never READY. No MD exceptions to chase - the failure
  is a silent wait, not a crash.

## Honest state of "why still no bars"
Every RF-table layer is now HTC-consistent and silent. The remaining
blocker is in the SIM/UIM state machine - likely one of:
  - UIM task waiting on an EINT/hot-plug or GPIO the HTC kernel named
    differently (MD1_SIM1_HOT_PLUG_EINT IPC query - kernel side answer).
  - The 'swi' crash source (the assert that fired when NVRAM was clear)
    may be a REAL data issue we masked again - diag+r10b combo needed
    (r10b still nops asserts; a diag variant of r10b would name it).
  - NVRAM version/sequencing: UIM waits for an NVDATA record that
    regenerates only after first successful registration (chicken-egg).
