## Interpretation
1. The whole EF-read sequence STARTS (iccid/service-table/ad/msisdn
   all enter). R22's "sim_select never runs" was the wrong dispatcher —
   USIM uses usim_select, which runs. Corrections logged.
2. The driver-level ready (post-ATR) fires, `usim_update_sim_to_ready`
   runs — so the low-level session IS established.
3. **The protocol-level SIM READY (`imc_mngr_sim_ready_req_handler`)
   is NEVER reached** — the IMS-side/protocol manager never receives
   the ready request. That's why RIL sees APPSTATE_DETECTED forever.
4. Probe caveat (honest): a crash proves FIRST ENTRY, not completion.
   The reads may start but never COMPLETE (each read is async: request
   out, confirmation back). The park could be:
   a) a confirmation never arrives/mismatches (async stall), or
   b) the completion chain stops before signaling protocol-ready.

## Where the park is (boxed)
Between "EF reads issued" and "protocol SIM READY signal":
- usim_initialization runs (starts reads) but its completion chain
  (all reads done → MMRR/USIM ready → imc_mngr) never fires.
- Prime suspect: an async read confirmation that returns an unexpected
  status (sw 0x91xx proactive-pending or 0x6Axx) which our old drop
  mishandles → the "all reads done" counter never completes → no ready.
